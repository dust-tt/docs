This page is the reference for roles and permissions in Dust. Admin governance separates three layers:

1. **Roles**, which describe a person's responsibility in the workspace.
2. **Governance capabilities**, which describe what groups of users are allowed to do.
3. **Resource access**, which describes which spaces, agents, skills, data sources and tools a person can access.

A person's effective permissions are the additive combination of the three. Nothing is subtracted: if any role or group grants an access, the person has it.

## Roles

### Admin

Admin is the full workspace administrator, typically held by IT or Security. An Admin can:

- Manage workspace administrators and all member roles.
- Configure IT & Security settings, including SSO and provisioning.
- Manage billing, subscriptions, seats, credits and per-member spending limits.
- Access and export audit logs.
- Configure governance capabilities, feature toggles, API keys, model providers and developer tools.
- Manage data connections, spaces and groups.

Admins always pass governance checks, regardless of how a capability is configured. Keep at least two Admins in every workspace so that access is never lost.

### Manager

Manager is a scoped operational administrator, typically a department lead or an internal champion. A Manager can:

- Open the Admin area.
- Invite and revoke members, and change non-admin roles.
- Assign the `manager` and `member` roles.
- Create manual groups and manage their membership.
- View workspace analytics.
- Edit member seat types, and view, approve or reject seat upgrade requests.

A Manager cannot promote or demote administrators, manage per-member spending limits, or access IT & Security, Billing, Workspace Settings, API keys, model providers, developer tools, or the governance toggles for billing, security, Frames and audit logs.

<Info>
  Manager is not the replacement for Builder. Builder capabilities are now controlled through governance capabilities and group membership.
</Info>

### Member

Members use the workspace according to their seat type, their space membership and the governance capabilities granted to them. Members have no administrative access by default.

Role and seat type are separate concepts: seat type controls what a person can consume, while role and capabilities control what a person can administer. Any role can hold any seat type.

## Groups and governance capabilities

Capabilities are granted to **groups**, not to individuals. There are two kinds of groups:

- **Provisioned groups**, synchronized from your identity provider through SCIM.
- **Manual groups**, created and maintained in Dust.

Permissions are additive. A person receives the union of the capabilities granted by their role and by every group they belong to. A group exception grants additional access; it never removes access granted through another role or group. To grant a capability to a single person, create a manual group with that person in it.

Each capability is configured in one of three modes:

| Mode | Who receives the capability |
| --- | --- |
| Everyone | All workspace members |
| Groups | Only the selected groups |
| Admin only | Only Admins |

### Available capabilities

| Capability | What it controls | Default |
| --- | --- | --- |
| Create agents | Who can create new agents | Everyone |
| Publish agents | Who can change an agent's publication state | Everyone |
| Create skills | Who can create new skills | Everyone |
| Publish skills | Who can change a skill's publication state | Admin only |
| View unpublished agents and skills | Who can discover and use resources that are not broadly published | Admin only |
| Access audit logs | Who can view and export workspace audit events | Admin only |
| Manage billing and security | Who can manage billing, subscriptions and security settings | Admin only |
| Manage Frame sharing and publication | Who can invite users to Frames or publish them externally, when the Frames feature is enabled | Admin only |

Publishing agents and publishing skills are separate capabilities. A person may be allowed to publish skills without being allowed to publish agents, or the reverse.

Three further administration areas can be delegated to groups in the same way: managing connectors, managing webhook sources, and managing remote MCP servers. Managing connectors and webhook sources is available to the configured groups by default; managing remote MCP servers is Admin only by default.

## Settings & Governance

Workspace administration is grouped under **Settings & Governance**. The rule is simple:

- Use **Governance** to control _who_ can perform an action.
- Use **Workspace Settings** to control _whether_ a feature is enabled.

Billing requires Admin, or the `Manage billing and security` capability. The audit logs toggle and the Frames feature toggle are configured on the Governance page and are Admin only. Disabling the Frames feature prevents all Frames usage, regardless of any capability granted to a group.

### Granting a capability to a group

1. Go to **Admin \> Settings & Governance \> Governance**.
2. Find the capability you want to change.
3. Set its mode to **Groups**, then select the groups that should receive it.
4. Save. The change applies immediately and is recorded in the audit log.

To grant a capability to one person, first create a manual group under **Admin \> Groups**, add the person to it, then select that group on the capability.

## Agents and skills publication

Agents and skills share the same publication model:

| State | Meaning |
| --- | --- |
| Unpublished | Available according to the workspace's policy for unpublished resources. Unpublished does not necessarily mean confidential. |
| Published | Available to the audience defined by the resource and by workspace access rules. |
| Discoverable | Surfaced for broader discovery according to the workspace's publication policy. |

Changing a publication state requires the relevant publish capability. Editing the content of an agent or a skill requires editor access. Being allowed to publish does not grant editing access, and being an editor does not grant publishing rights.

For skills, publication state is distinct from the skill status exposed by the API (`active`, `archived`, `suggested`), which describes the lifecycle of the skill rather than who can see it.

## Migration from Builder

Builder is no longer used as a workspace role or as the long-term permission model.

- In every workspace that had active builders, a group named **Builders** is created and granted `Create agents` and `Create skills` for the whole workspace, and existing builders are added to it.
- Assigning the legacy `builder` role now adds the person to that group.
- Administrators can move these capabilities from the Builders group to any other manual or provisioned group at any time, and can delete the group once its members are covered elsewhere.

Some behaviours previously attached to the Builder role have moved or been retired:

| Former Builder behaviour | Now |
| --- | --- |
| Enable or disable global agents | Admin only |
| Read, delete or rename files in any space | Admin only |
| Link Slack channels and set the default Slack responder | Granted with `Publish agents` |
| See the Insights tab | Granted with `Publish agents` |
| Moderate or edit feedback on any agent | Requires editor access on the agent |
| Add or remove the Company tag on an agent | Retired |
| The "builders" audience for global agents | Retired |
| Create folders or web crawlers in an open data source | Retired |

### Legacy role values in the API

Existing integrations keep working during the migration period:

| Legacy value | Behaviour now |
| --- | --- |
| `admin` | Maps to Admin |
| `builder` | Removed from API keys. The Builders group is attached to affected keys instead, so creation rights are preserved |
| `user` | Maps to Member |

Update integrations to the current role values before the end of the migration period, and grant capabilities through groups rather than relying on legacy values.

## FAQ

**Does Manager replace Builder?** No. Manager is an operational administrator role. Agent and skill creation rights come from governance capabilities and group membership.

**Can Managers manage billing or security?** Not by default. Billing and security require Admin, or the `Manage billing and security` capability.

**Can I give one person a capability without creating a group?** No. Create a manual group containing that person, and grant the capability to the group.

**Are publishing agents and publishing skills the same permission?** No. They are separate capabilities and can be granted independently.

**Can a Manager see restricted spaces?** No. Space access is governed by space membership and groups.

**What happens if a person is in several groups?** Capabilities are additive. The person receives the union of everything their role and their groups grant.

**Does a capability set to Admin only still apply to Admins?** Yes. Admins pass every governance check, whatever the mode.

**Who can see that a permission changed?** Role changes, capability changes, capability mode changes and group membership changes are recorded in the audit log.
