title: "Memberships & Roles"
---

You can manage members (invite, revoke, change role, see member list) by going to **Admin > Workspace & Governance > People**.

Dust uses a three-role model that expresses a person's **responsibility** in the workspace. Roles are one layer of a broader governance model—see [Admin governance](/docs/user-documentation/admins/users-and-permissions-management/admin-governance) for the full picture, including governance capabilities and group-based access.

## Workspace Roles

### Super Admin

Super Admins hold full workspace administration authority (typically an IT or Security persona). They can:

- Manage workspace administrators and security settings (SSO, audit logs)
- Configure billing, governance settings, and data connectors
- Manage spaces, groups, and workspace feature toggles
- Manage API keys, model providers, developer tools, and analytics

Super Admins always pass every governance capability check regardless of how capabilities are configured.

### Manager

Managers are operational administrators (champions, department leads) with scoped access to the Admin area. They can:

- Invite, revoke, and update members (non-admin roles only)
- Create and manage manual groups; add or remove people from groups
- Assign `manager` and `member` roles
- View analytics and edit member seat types
- View, approve, and reject seat requests

Managers **cannot**: manage Super Admin accounts; access IT & Security settings (SSO, audit logs toggle, Frames toggle); manage API keys, model providers, developer tools, or billing; or control per-member spending limits.

### Member

Members use workspace resources according to their seat type, space membership, and the governance capabilities granted to them through groups. They have no administrative access by default.

## Seat Type vs. Role

A member's **role** (Super Admin, Manager, Member) determines administrative responsibilities. Their **seat type** controls which workspace features they can consume (e.g. full usage vs. light usage). These are independent: a Manager can have any seat type, and a Member's seat type may grant different resource quotas without affecting their governance access.

## Governance Capabilities and Groups

Roles alone do not determine everything a user can do. **Governance capabilities** (such as `Create agents`, `Publish agents`, `Create skills`, `Publish skills`, `Access audit logs`) are granted through **groups**. Permissions are **additive**: a person gains the union of what their role and all their group memberships grant.

Each governance capability can be set to one of three modes:
- **Everyone** — all workspace members have this capability
- **Groups** — only members of the designated groups have this capability
- **Admin only** — only Super Admins have this capability

See [Admin governance](/docs/user-documentation/admins/users-and-permissions-management/admin-governance) for the full list of capabilities and their default modes.

## Builder: Migration Note

<Note>
**Builder is a legacy role** and is no longer a current role in the governance model.

Workspaces that had active Builders have been migrated to a **Builders** group granted the `Create agents` and `Create skills` capabilities for the whole workspace. Former Builders are members of this group. Admins can reassign these capabilities to other manual or SCIM-provisioned groups as needed.

During the migration period, the legacy `builder` role value remains accepted in the API for compatibility; it maps to Builders group membership rather than a distinct role.
</Note>

## Handle memberships & roles through provisioning

User roles and memberships in Dust can be managed through automated provisioning. While manual invitation remains available, enterprise customers can configure automated user management through SCIM 2.0 integration with their Identity Provider (IdP). See [Users and groups provisioning](/docs/user-documentation/admins/users-and-permissions-management/users-and-groups-provisioning).
