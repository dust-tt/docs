---
title: "Credits usage"
---


A trigger run costs credits like any other agent run. The **Credits** setting on each trigger decides whose credits pay for it: the trigger editor's, or the workspace. It does not change anything else about how the trigger behaves.

## Set the pool on a trigger

Open the trigger in the Agent Builder and pick from the **Credits** dropdown:

- **My credits** bills the run to the trigger editor's credits, as if they had sent the message themselves. It is the default on credit-priced plans. **On legacy plans, new triggers can no longer use it**: only triggers created before September 1, 2026 and still on **My credits** keep it (see [Pools on legacy plans](#pools-on-legacy-plans)).
- **Workspace credits** bills the run to the workspace as programmatic usage, alongside API calls and other automations. It is not attributed to any member. On legacy plans, all new triggers must use this pool.

To change the setting you must be an editor of the agent and have access to the workspace pool, which an admin grants (see [Grant access to the workspace pool](#grant-access-to-the-workspace-pool)). Without that access, you can see the setting but not change it. Admins and managers can also change it from the Automations page. Your changes are automatically picked up starting from the next run.

## Pools on legacy plans

Legacy plans still use message quotas instead of credits. Since September 1, 2026, triggers on these plans follow these rules:

- **New triggers use Workspace credits.** You can't select **My credits** when you create a trigger. The trigger form still opens on **My credits** and shows *Your plan doesn't support charging automations to personal credits.* Switch the dropdown to **Workspace credits** to save the trigger.
- **Triggers already on My credits keep it.** They keep running on **My credits** and you can still edit them, as long as you leave their pool unchanged.
- **Moving a trigger to Workspace credits is one-way.** Once a trigger is saved on **Workspace credits**, it can't go back to **My credits**, either from the trigger or from the Automations page.
- **Creating a trigger requires access to the workspace pool.** Only admins have it by default. Members without it see *Automations on your plan must be charged to the workspace credit pool, which you don't have permission to use. Ask a workspace admin for access.* and can't save the trigger. An admin can grant this access as described in [Grant access to the workspace pool](#grant-access-to-the-workspace-pool).

## Which pool to pick

Put a trigger on workspace credits when it serves the team rather than one person: PR reviews, ticket triage, alert routing, anything running dozens of times a day. Charging that to one member's seat credits exhausts them on work the team benefits from.

Leave a trigger on personal credits when its editor is also the one who reads the output, like a morning digest or a weekly report. Volume stays low and the cost sits with the person who asked for it.

On legacy plans, this choice only applies to triggers already on **My credits**. New triggers use workspace credits.

## Grant access to the workspace pool

Only admins can charge triggers to the workspace by default. Admins and managers set this under **Governance > Pods & Frames > Automations > Charge automations to the workspace**. They can choose everyone, selected groups, or admins only.

On legacy plans, new triggers must use workspace credits, so members need this access to create triggers.

Removing the access does not move existing triggers back to personal credits. Triggers already on workspace credits stay there until someone changes them.

## Where the credits come from

On credit-priced plans:

- **My credits** uses the editor's seat credits first, then the workspace credit pool if their seat has access and their personal spend limit allows it. [Credit management](/docs/user-documentation/admins/usage-seats-and-credits/credit-management) covers that order in detail.
- **Workspace credits** uses the workspace credit pool, then Pay As You Go on Enterprise plans. It counts against the monthly programmatic cap in **Admin > Credits**, **Settings** tab and has no free credit baseline.

On legacy plans, which still use message quotas instead of credits:

- **My credits**, which only triggers already on it can keep (see [Pools on legacy plans](#pools-on-legacy-plans)), counts against the workspace's fair-use message allowance. Webhook triggers can use up to half of it, leaving the rest for people's conversations.
- **Workspace credits** uses programmatic usage credits, the balance shown in **Admin > Credits**, **Programmatic usage** tab, and counts against the monthly programmatic limit.

<Note>
A trigger stops running once the pool it charges is out: its editor's credits or personal spend limit on **My credits**, the workspace pool or the monthly programmatic cap on **Workspace credits**. Admins can add credits from **Admin > Credits** and raise the monthly cap under **Admin > Credits**, **Settings** tab. The trigger starts running again once the limit resets or the balance goes back up, and runs missed in the meantime are not replayed.
</Note>

## Review your triggers

Admins and managers see every trigger in the workspace under **Admin > Automations**, with its agent, its credit consumption over the selected period, and a **Pool** column showing *Member* or *Workspace*.

Members can review their own automations from the **Automations** entry under **Tools** in the user menu. This view lists the automations they edit, with filters, an expandable per-trigger credit breakdown for the current billing cycle, and controls to enable, disable, or delete an automation.

Select several rows to move them to another pool in one go, which is the quickest way to migrate a batch of triggers after changing your policy.

## Rate limits

The pool is separate from the rate limit. A webhook trigger keeps its own cap on runs per 24 hours whichever pool it charges. See [Rate limiting](/docs/user-documentation/agents/triggers/webhooks/rate-limiting).
